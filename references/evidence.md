# 审查、证据与交付

评审依据是当前用户任务、既定规范和目标平台。把可检查的质量问题、任务/业务约束和审美偏好分别说明；模板偏好不能自动推翻项目决定。

## 问题记录

每个需要处理的问题给：位置/状态、可观察证据、用户影响、建议修改位置和优先级。优先级依据如下：

- **P0**：主要动作不可达、输入丢失、误报成功、核心信息被遮挡/不可读等直接阻碍任务的问题。
- **P1**：明显增加理解或操作成本、共享规范漂移、重要状态反馈/可访问性缺失。
- **P2**：不影响当前任务完成的审美精修或可选增强。

证据只有源码时说明推断条件；真实截图/操作时注明对应状态。不能从未查看的截图给视觉评分，也不能把主观“更高级”作为唯一修复理由。评审请求保持只读；明确要求修复时实施其范围内的修改。

## 取证尺度

| 改动 | 需要的证明 |
| --- | --- |
| 单个间距/控件/文案 | 实际改动区域和相邻元素；相关状态/主动作 |
| 页面美化/响应式 | 前后同状态/尺寸画面；目标断点、长内容及关键操作 |
| 共享 token/组件重构 | 代表性调用者前后画面；状态/行为回归与相关检查 |
| 保存/流程改变 | 真实入口到结果；重读；失败恢复；受影响的生命周期 |
| 动效/手势 | 查看实际播放/录屏或具有时序的证据；减少动态效果与中断 |
| 截图还原 | 参考视口/状态一致的比较；布局/排版/裁切与实际差距 |

截图保存后实际查看，必要时用图片查看工具；程序测量补充视觉观察。长页看完整节奏和关键局部。前后对比保持内容和状态可比，不把测试过程中输入改变当成设计差异。

按实际平台运行，不能用本地网页证明 Chrome 扩展的生命周期，也不能用网页截图证明原生 App。取证工具与授权沿宿主实际能力，选用适用工具即可，不要求安装固定测试框架。

## 状态字段

按视觉、交互、平台分别报告：

| 状态 | 含义 |
| --- | --- |
| `verified` | 指定范围已实际执行并检查，有对应证据 |
| `partial` | 只验证部分状态、视口、设备或操作，列出具体已测范围与缺口 |
| `unrun` | 该维度未执行，不把预测或静态检查当作运行结果 |

构建成功、静态分析、单元/集成检查单独列出。代理文字方案验证的是决策，不能计入浏览器或设备 E2E。只有源码的交付可以说明已编辑和静态结果，视觉、交互、平台仍按真实执行填写。

## 集中修复与收敛

用一轮集中评审找出最影响主任务的少量问题，修复后复查受影响范围。仍有明确功能/可用性缺陷则继续处理；偏好反复或新方向超出当前范围时陈述取舍，保留当前可用结果，不以无限追分替代交付。

独立视觉评审仅在任务需要且隔离/看图能力和授权允许时进行。评审者接收当前画面、任务、范围和必要规范；不能把同一代理自检称为独立评审。大型改版可邀请评审，小改动不默认增加角色和调用。

## 交付合同

用三部分说明，短任务可以各一句：

1. **改动与理由**：目标范围、实际文件/页面、对任务的改善及关键保留项。
2. **实际验证**：运行的检查；视觉/交互/平台的状态；页面/状态/视口或设备、版本与证据路径。
3. **剩余项**：未完成或未运行内容、原因和具体所需条件；全部范围已完成时简述无剩余项。

记录放在项目已有任务/输出位置；技能目录只放可复用规则。项目已有设计决定文件更新实际变化，避免新增相互冲突的规范。
